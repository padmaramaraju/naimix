How it works

The mental model: a shared collection of building blocks, and apps that expose them.

The request flow

incoming request
   │
   ▼  route match (method + path)         ← defined in an App
   ▼  extract & validate input params    ← path / query / header / body / env
   ▼  caller authentication (if required) ← gateway's requiresAuth
   ▼  call the backend                    ← json | xml | soap | sql, via a Gateway
   ▼  map response onto output shape      ← JSONPath in, dot-path out, transforms
   ▼
JSON response

The building blocks

ConceptOwned byWhat it is
GatewayShared CollectionA reusable connection to one backend: base URL or WSDL, database connection, headers, common parameters, and optionally requiresAuth.
IntegrationShared CollectionHow to call a backend and shape its response: input, backend and output. It has no public URL of its own.
Auth providerShared CollectionHow callers log in: a bespoke login API, OAuth2, or LDAP/AD.
FunctionShared CollectionA custom transform function referenced by name from an integration's output mapping.
RouteAppA public method + path that points at one integration by name.
AppConsuming teamA list of routes. Think of it as a backend-for-frontend (BFF) assembled from the shared catalog.

Shared Collection vs. App

This split mirrors patterns from API gateways such as Kong (Service and Route) and AWS API Gateway (Integration and Resource).

  • The Shared Collection (called the Workspace in config and code) is maintained centrally. It holds gateways, auth providers, integrations and functions.
  • An App belongs to a team that consumes the collection. It contains no backend-calling logic. It only assembles routes out of what the collection already offers.
  • A route is a pure pointer. If a team needs different call or mapping behavior, the answer is to define a different integration.

Authentication composes automatically: requiresAuth lives on the gateway, so every route whose integration calls through that gateway requires a session from that provider.

Where things live on disk

<workspace>/            # one folder, typically its own Git repo
  gateways.yaml
  authProviders.yaml
  integrations/         # one YAML file per integration
  apps/                 # one YAML file per app (id, name, routes)
  transforms/           # custom functions (.ts source + compiled .js)

The bundled demo in config/ still contains a legacy endpoints/ folder alongside integrations/ and apps/. The server reads integrations and apps. A migration script (npm run migrate:endpoints) converts the old combined format into the split one.

Three build targets, one core

naimix builds as dev, qa or prod. All three share the same request-handling core. Only dev includes the Developer Console, and the QA and Production bundles are checked at build time to prove none of that code leaked in. See QA & Production.
