QA & Production

The Developer Console is a development-only tool. QA and Production use separate builds that never contain that code at all.

Three targets, one core

TargetEntry pointnpm scriptsDeveloper Console
devsrc/server/index.tsnpm run dev, or npm run build && npm startPresent, gated by CONSOLE_TOKEN
qasrc/server/qaIndex.tsnpm run dev:qa, or build:qa then start:qaNot present
prodsrc/server/prodIndex.tsnpm run dev:prod, or build:prod then start:prodNot present

qa and prod run identical code today. They differ only in their startup log line. They are kept as separate entry files so they can diverge later without threading conditionals through shared code.

Build and run

npm run build:qa     # → dist-qa/server.js
npm run build:prod   # → dist-prod/server.js

npm run start:qa
npm run start:prod

Each build bundles first-party code with esbuild (node_modules stays external, so it must be installed next to the bundle) and then runs scripts/checkDataPlaneBundle.js. That script searches the bundle for console-only identifiers such as requireConsoleAuth and createConsoleApiRouter and fails the build if any appear. It is a structural proof that the separation holds, not just a comment saying so.

Configuring an instance

  1. Put the workspace on the server, typically a shared volume populated by your promotion pipeline, and set CONFIG_DIR to it (or the legacy variables).
  2. Place this environment's own deployment.yaml with its mounts. With no mounts the server starts with zero routes and logs a warning. DEPLOYMENT_FILE overrides its location.
  3. Set secrets (${env.*} values) in the server's environment or secrets manager.
  4. Set OPS_TOKEN if you want the Ops Console.

CONSOLE_TOKEN and the console's "Change workspace" feature do not exist in these builds.

The promotion model

The design notes recommend this flow, which fits the file-based config model:

  1. A developer changes config in a dev instance. It is written to the workspace files.
  2. The workspace is a Git repo, so the change is committed and tested in dev and QA like any code change.
  3. When ready, the change is merged to a Production branch.
  4. Ops pulls that branch onto the volume the production instances mount.
  5. Instances are restarted, ideally in a rolling manner, to pick up the new files.

A full restart is the only update mechanism in production. There is no live reload, which keeps "config went live" an explicit, auditable action and makes rollback the same mechanism as rollout.

Parts of DEPLOYMENT_ARCHITECTURE_NOTES.md (shared network volume, Redis-backed sessions across instances) are design notes and not implemented. Sessions are currently in-process memory, so run a single instance or use sticky routing until that lands. See Known limitations.
