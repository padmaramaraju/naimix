Workspace & Git

Each person runs their own naimix instance on their own machine. Teams share work through a Git repo, not through a shared server.

What a workspace is

A workspace is any folder with this layout (the same as the project's own config/ folder):

integrations/        # one YAML file per integration
apps/                # one YAML file per app
gateways.yaml
authProviders.yaml
transforms/          # custom functions (optional)

The folder must already exist (it is your Git checkout), but the files inside it do not. Each is created the first time you save something.

Pointing an instance at a workspace

In priority order:

  1. Console UI. Click Change workspace… in the bar under the header, then Browse folders…, navigate to your folder, click Select this folder, and save. You can also type a path. The picker lists folders on the machine running naimix, because browsers do not expose absolute paths. The choice is written to configDir in deployment.yaml and reused on the next start. Integrations and gateways switch over immediately with no restart.
  2. Hand-edit deployment.yaml: set configDir.
  3. CONFIG_DIR env var. Handy for a first run or scripted setup.
  4. Legacy variables INTEGRATIONS_DIR, APPS_DIR, GATEWAYS_FILE, AUTH_PROVIDERS_FILE, TRANSFORMS_DIR point at each piece independently.

Choosing a workspace never changes mounts. Which apps are served, and where, stays a hand-edited decision. If you switch to a workspace whose apps are not mounted, you will get no routes. See Mounting apps.

Working with Git

naimix never runs git for you. Checking out or pulling a workspace, and committing or pushing your changes, is something you do with your usual tools before or after using the app. Two teammates can have different workspaces or branches open at once. Resolving differences is an ordinary Git merge.

Keeping a checkout self-contained

The UI always saves an absolute path. To make a checkout portable, set configDir in deployment.yaml to a relative path such as config. It resolves against the folder you run the app from, so moving the checkout never leaves a stale absolute path.

Committing safely

  • The shipped config/ demo reads every connection detail from ${env.*} placeholders, so it is safe to commit.
  • If your real gateways.yaml contains a literal credential, do not commit it. Move the credential to an env var (recommended), or add a local-only /config/ line to your own .gitignore.
  • .env and deployment.yaml are already ignored by Git.
