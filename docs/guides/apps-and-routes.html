Apps & Routes

An App is a team's own backend-for-frontend, assembled from the Shared Collection. It is a list of routes, each pointing at an integration.

A route

# apps/default.yaml
id: default
name: Default App
routes:
  - id: json-customer-by-id
    method: GET
    path: /api/json/customers/:id
    description: Fetch a single customer from the demo JSON REST backend.
    integration: json-customer-by-id
FieldMeaning
idStable identifier, separate from method and path so you can change a path without breaking references.
method + pathThe public URL. Express-style, with :params.
integrationName of the integration this route calls.
descriptionShown in the console and in exported specs.

A route carries no input, backend or output overrides. If a team needs different behavior, create a different integration.

App ids and names

An app has a stable id (a slug) and an editable display name. Renaming the label never breaks anything that refers to the id.

Create an app and routes in the console

  1. Click + New App in the sidebar and type a name. Save it on the Settings tab; the Routes and Export tabs unlock once it exists.
  2. On the Routes tab, add a route: choose the method, type the path, and pick an integration.
  3. Use the route's own Try it tester to call it. This is separate from the integration-level Test tab.

The server checks for collisions between routes, including ones that differ only in path parameter names (for example /customers/:id and /customers/:customerId).

Mounting apps on a server

Defining an app is not enough to serve it. deployment.yaml describes what a given server instance serves: which workspace to load, and which apps to mount at which public path prefix. It is hand-edited per environment (like .env) and not committed to Git. Copy deployment.yaml.example to start.

configDir: /path/to/your/workspace-repo/config

mounts:
  - app: default          # the app's id
    basePath: /           # public prefix
  - app: web-bff
    basePath: /web-bff
KeyMeaning
configDirThe workspace folder (integrations/, apps/, gateways.yaml, authProviders.yaml, transforms/). In dev, the console's Change workspace… button updates this value for you.
mounts[].appThe id of an app in the workspace.
mounts[].basePathPublic prefix that app's route paths are served under. Several apps can share a server without colliding.

No mounts means no routes. A missing deployment.yaml, or one without mounts, makes the server start with zero routes even though integrations and apps exist on disk. This is intentional. The server logs a warning when it happens. The comment in deployment.yaml.example calling mounts "planned" is out of date; the server reads it.

Even a server serving only one app should list it with its own basePath, so adding a second app later never changes existing public URLs. In QA and Production, the deployment team places that environment's own deployment.yaml on the server as part of promotion. Set a different location with DEPLOYMENT_FILE.
