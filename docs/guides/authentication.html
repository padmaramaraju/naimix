Caller authentication

Protect your data endpoints. naimix logs in to the real backend on the caller's behalf, keeps the backend token server-side, and hands the caller an opaque session token instead.

This is separate from CONSOLE_TOKEN, which only guards the Developer Console. Caller authentication guards the endpoints you define under /api/….

How it fits together

  1. Define a provider in authProviders.yaml.
  2. Require it by adding requiresAuth: myProvider to a gateway. Every route calling through that gateway now needs a session from that provider.
  3. Callers log in once: POST /auth/login/myProvider with {"username":"…","password":"…"}. They get { "token": "…", "expiresAt": … }.
  4. Callers send the token as Authorization: Bearer <token> on later calls.
  5. Use the real token on the backend through the reserved {__authToken} parameter, for example in a gateway header.
  6. Log out with POST /auth/logout. Opaque tokens are a server-side lookup, so revocation is instant.
gateways:
  crmJsonAuthed:
    kind: json
    baseUrl: ${env.CRM_BASE_URL}
    requiresAuth: myProvider
    headers:
      Authorization: "Bearer {__authToken}"

Provider kinds

basicLogin: a bespoke login API

myProvider:
  kind: basicLogin
  loginUrl: ${env.BACKEND_LOGIN_URL}
  tokenPath: $.accessToken           # JSONPath into the login response
  refreshTokenPath: $.refreshToken   # optional
  expiresInPath: $.expiresIn         # optional, seconds

oauth2: a standard RFC 6749 token endpoint

myOAuthProvider:
  kind: oauth2
  tokenUrl: ${env.BACKEND_TOKEN_URL}
  grantType: password       # or client_credentials, or authorizationCode
  clientId: ${env.BACKEND_CLIENT_ID}
  clientSecret: ${env.BACKEND_CLIENT_SECRET}

client_credentials takes no end-user credentials, since it authenticates the middleware itself. Sessions refresh automatically a little before expiry via the standard refresh_token grant.

ldap: LDAP / Active Directory simple bind

myLdapProvider:
  kind: ldap
  url: ${env.LDAP_URL}                  # ldap://… or ldaps://…
  bindDn: cn=admin,dc=example,dc=com
  bindPassword: ${env.LDAP_BIND_PASSWORD}
  searchBase: ou=people,dc=example,dc=com
  searchFilter: (uid={username})        # (sAMAccountName={username}) for AD
  groupSearchBase: ou=groups,dc=example,dc=com   # optional
  groupSearchFilter: (member={dn})
  attributes: [mail, title]
  tokenSecret: ${env.LDAP_TOKEN_SECRET}

LDAP has no native token, so on a successful bind naimix mints a signed HS256 JWT (sub, username, and groups when configured) as the stand-in backend token. A backend sharing the same secret can verify it. Expired LDAP sessions return a clean 401; there is no refresh.

Two modes exist: search-then-bind (shown above, the usual enterprise pattern) and direct bind via userDnTemplate. Configure exactly one.

OAuth authorization code (browser redirect)

For a human logging in on the identity provider's own page, so naimix never sees a password:

myOAuthCodeProvider:
  kind: oauth2
  grantType: authorizationCode
  tokenUrl: ${env.IDP_TOKEN_URL}
  authorizationUrl: ${env.IDP_AUTHORIZATION_URL}
  redirectUri: ${env.NAIMIX_OAUTH_REDIRECT_URI}   # naimix's OWN callback
  clientId: ${env.IDP_CLIENT_ID}
  clientSecret: ${env.IDP_CLIENT_SECRET}
  clients:                                        # allow-list of calling apps
    - id: myWebApp
      returnTo:
        - https://app.example.com/oauth-done

A client app opens this in a browser (not as an API call):

GET /auth/oauth/myOAuthCodeProvider/start?app=myWebApp&return_to=https://app.example.com/oauth-done&state=<optional>

After login, naimix redirects to return_to with its own session token in the URL fragment (#token=…&expires_at=…). A fragment is visible to your app's JavaScript but never sent to any server, including naimix's own logs.

  • redirectUri is naimix's address, registered with the provider. returnTo is where naimix sends the user afterwards. They are different things.
  • clients is a closed allow-list: any app and return_to pair that is not an exact match is rejected, which prevents open redirects.

Manage providers in the console

Use Auth providers in the Shared Collection (list, create, edit, delete). A blank clientSecret on edit means unchanged. A gateway's editor has a Requires auth dropdown. Deleting a provider that a gateway still requires is refused with a 409.

Try it locally

  • demoLogin: POST /auth/login/demoLogin with demo / demo123.
  • demoLdap: run npm run test-ldap (needs Docker), then log in as jdoe, asmith or bwayne with password password123.
  • demoOAuthCode: open the /auth/oauth/demoOAuthCode/start?… URL from config/gateways.yaml in a browser and click through the mock provider.

Single instance only: sessions and pending OAuth logins live in one process's memory. Behind a load balancer with several instances this does not work yet. See Known limitations.
