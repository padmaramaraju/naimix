Generated CRUD endpoints

For a SQL gateway, the console can introspect the real database and generate integrations for every table and stored procedure, instead of hand-writing one file per table.

Generate them

  1. Create and save a SQL gateway (it must already be saved).
  2. Open it and click Generate CRUD + procedure endpoints.
  3. Review the report. Anything that conflicted is listed as skipped.

Generation never overwrites. An id or method+path already in use is skipped and reported, so it is always safe to run again, for example after adding a table.

What you get per table

At /api/<gateway>/<table>:

MethodId suffixWhat it does
GET-listList and filter rows.
POST-createBulk insert rows.
PATCH-updateBulk update rows by primary key.
DELETE-deleteBulk delete rows by primary key.

A table with no primary key only gets -list and -create, since there is no reliable way to target a specific row.

Listing: query string filters

  • Any real column name does an exact-match filter, for example ?status=ACTIVE.
  • limit and offset paginate. Default limit is 100, maximum 1000.
  • sort and order (asc or desc) order the rows.
  • For a single-column primary key, ids=1,2,3 fetches specific rows.
  • Unrecognized keys are ignored, not errors.

Bulk writes: JSON body

// POST /api/mainDb/customers
{ "rows": [ { "first_name": "Ada", "status": "ACTIVE" }, { "first_name": "Grace", "status": "ACTIVE" } ] }
// → { "insertedCount": 2, "rows": [...] }

// PATCH /api/mainDb/customers
{ "updates": [ { "key": { "id": 1 }, "fields": { "status": "INACTIVE" } } ] }
// → { "updatedCount": 1, "results": [ { "key": {...}, "matched": 1 } ] }

// DELETE /api/mainDb/customers
{ "keys": [ { "id": 1 }, { "id": 2 } ] }
// → { "deletedCount": 2, "results": [ ... ] }
  • Each key must contain exactly the primary key column(s). Missing or extra columns give a 400.
  • All rows in one request run in a single transaction, all or nothing.
  • A missing, empty or wrongly shaped array gives a clear 400, not a 500.
  • Full inserted rows come back (rows) only on pg and mssql. MySQL and SQLite return rows: null with just the count.

Stored procedures

One endpoint per procedure at POST /api/<gateway>/proc/<name>, with one body parameter per procedure parameter. The raw result is returned under a single result key. Unlike table endpoints, these work in the Try it panel.

ClientSupported
pgYes, via CALL. A CALL does not return a row set like a function, so a procedure that relies on OUT parameters may need a function wrapper.
mysql2Yes, via CALL.
mssqlYes, via EXEC.
sqlite3 / better-sqlite3No. SQLite has no stored procedures.

Limits to know

  • Filters are exact-match only: no ranges, OR or LIKE.
  • Table and procedure names are generated only if they match [A-Za-z0-9_]+. Others are skipped and reported.
  • Generated endpoints show as a read-only summary in the editor. To pick up a schema change, regenerate rather than hand-edit.
  • The pg, mysql2 and mssql paths were not exercised against a live server during development (only SQLite was available). Test against your own server first.
