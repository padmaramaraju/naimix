Developer Console

A browser UI for creating gateways, integrations, apps and routes, then testing them against real backends. Changes take effect on the very next request, with no restart.

Enable it

  1. Set CONSOLE_TOKEN in .env to any random string. .env.example has a generator command.
  2. Run npm run dev (or npm run build && npm start).
  3. Open http://localhost:4000/console and enter the token. The browser remembers it in local storage.

The console can configure an integration that calls any URL or SQL query the process can reach, so it is gated by a bearer token and disabled entirely (503) when no token is set. It exists only in the dev build. See QA & Production.

Layout

  • Shared Collection (left sidebar): Integrations, Gateways and Auth Providers. Each opens a catalog table in the main panel, with an + Add button.
  • Apps (left sidebar): your apps, with + New App to add one. An app has three tabs: Settings, Routes and Export.
  • Active sessions: who is currently logged in through each auth provider, with a refresh button.
  • Workspace bar: shows which folder you are editing, with counts, and a Change workspace… button.
  • A sun/moon switch toggles light and dark. By default it follows your OS.

Editing an integration

The integration editor has tabs so only one section is on screen at a time. Each tab shows a running summary, for example Backend (json · crmJson).

TabWhat you set
BasicId and description. The used by line shows which routes call it.
BackendPick a gateway first. The type is then set from it and greyed out, because the two can never disagree. Type stays editable only when gateway is "(none)", for calling a URL directly.
ParametersInput parameters: name, location (path, query, header, body, env), type, required, default.
OutputField mapping: target, source JSONPath, transform, default. Add nested arrays, and attach a post-process function.
TestThe "Try it" panel (below).

The Try it panel

  1. Fill in sample values for your input parameters.
  2. Click Fetch sample response to call the real backend now and see its raw response.
  3. Click Apply mapping to sample to see what your current output config produces from it.

This works without saving first, and without re-calling the backend each time you tweak the mapping. For an env parameter, the value box is an optional override on top of the real environment value.

Other handy features

  • Field info icons. Every field has a small "i" with a short explanation. Click it again, click elsewhere, or press Escape to close it.
  • View gateway. On the Backend tab, a button pops up the selected gateway's definition without leaving the editor.
  • Test connection. On SQL gateways, opens the database with the form's current settings and reports success or the driver's real error, without saving. A blank sensitive field tests against its stored value.
  • Generate CRUD + procedure endpoints. On a saved SQL gateway. See Generated CRUD endpoints.
  • Custom functions. In an integration's Output tab, the Transform picker (and the post-process picker) has a + New function… option that opens an inline code editor with a Test button. See Transform functions.
  • Reload from disk. Re-reads the workspace after you hand-edit YAML.
  • Masked secrets. Fields that look sensitive (password, token, secret, apiKey) are masked once saved. Leaving one blank when editing means "unchanged".
  • Dependency protection. Deleting a gateway that an integration still uses is refused with a 409 listing the dependents. The same applies to auth providers used by gateways.

Things worth knowing

  • Saving through the UI rewrites gateways.yaml in full, so hand-written comments in that file are lost after the first UI edit. The same applies to an individual file once edited (not created) in the UI.
  • A gateway field can hold ${env.VAR_NAME} or a literal. A literal secret is written to disk in plain text, so prefer the env form.
  • The console uses one shared CONSOLE_TOKEN, not per-user accounts. That is fine for a small team or personal use.
