OpenAPI & MCP export

Hand your workspace to other tools. Both exports reflect the current config at the moment you download them, so just download again after making changes.

OpenAPI spec

Open an app in the console and use its Export tab, which offers the OpenAPI download for that app's routes. Or script it:

curl -H "Authorization: Bearer $CONSOLE_TOKEN" \
  http://localhost:4000/console/api/export/openapi.json

The result is an OpenAPI 3.0.3 document describing every configured route (as its real caller-facing method and path), plus the built-in /auth/login/{provider}, /auth/logout, /healthz and /__endpoints routes. Import it into Postman, Swagger UI, or a code generator. A route whose gateway requires auth is marked with a bearer-token security requirement naming the provider to log in through.

The Export tab covers only that app's own routes, via /console/api/apps/<appId>/export/openapi.json. The workspace-wide spec above covers every route.

MCP server

The Export tab's MCP server download (or GET /console/api/export/mcp-server) gives you a single dependency-free file, naimix-mcp-server.js, that turns your workspace into an MCP server for any MCP client such as Claude Desktop or Claude Code.

It is a thin proxy, not a snapshot. Each time it starts, it asks your live naimix instance which routes, gateways and auth providers exist and builds its tools from that. After a config change, just restart the MCP client. It needs only Node.js 18+ and no npm install.

{
  "mcpServers": {
    "naimix": {
      "command": "node",
      "args": ["/absolute/path/to/naimix-mcp-server.js"],
      "env": {
        "NAIMIX_BASE_URL": "http://localhost:4000",
        "NAIMIX_CONSOLE_TOKEN": "your CONSOLE_TOKEN value"
      }
    }
  }
}

You get one login_<provider> tool per auth provider (taking username and password, except an OAuth2 client_credentials provider), a logout tool, a list_endpoints tool, and one tool per route. Log in with the right login_* tool before calling a tool whose route requires it; the tool description says which.

NAIMIX_CONSOLE_TOKEN is used only to discover the workspace's shape. Tool calls go through the normal public routes. Treat the file plus that token as a credential: together they give full console access to whatever NAIMIX_BASE_URL points at.

This works only against a dev build. QA and Production do not expose /console/api/*, so there is nothing to discover. Point NAIMIX_BASE_URL at a dev instance.
