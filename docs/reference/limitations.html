Known limitations

What naimix does not do yet, so you can plan around it.

Mapping

  • Mapping is field by field. There are no built-in computed or concatenated fields or conditionals. Use a custom function for those. A JSONata or JMESPath mode would be a natural extension.
  • Custom functions must be synchronous and pure.

Authentication and scaling

  • Sessions and pending OAuth logins live in one process's memory, so this does not yet work behind a load-balanced multi-instance deployment. A shared store (Redis was considered) is designed but not built.
  • SAML is designed but not implemented. LDAP is plain simple bind only, with no Kerberos or SPNEGO single sign-on.
  • A gateway with no requiresAuth is unauthenticated.
  • The Developer Console uses one shared CONSOLE_TOKEN, not per-user accounts or roles. A multi-user deployment would want real auth in front of /console.

Backends

  • The SOAP connector caches one client per WSDL URL. If you need several concurrent endpoints behind the same WSDL URL, split them into separate gateways.
  • Generated CRUD filters are exact-match only, and bulk update and delete target rows strictly by primary key.
  • The PostgreSQL, MySQL and SQL Server introspection and procedure paths were not tested against live servers in development. Test against your own.

Operations

  • QA and Production update only by restart. There is no live reload.
  • The Ops Console currently has system and environment panels only. Metrics, logs and request capture are designed but not built.

Design notes

The repository's *_DESIGN_NOTES.md files record the reasoning and future plans for authentication, deployment, the Ops Console, apps and transform functions. Where they describe something as planned, treat it as not available.
